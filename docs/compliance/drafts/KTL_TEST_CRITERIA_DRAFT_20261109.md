## M01 수집정확도

회의 방향은 대표 동작 약10회, 목표65%다. 사람이 수행하는 동작, 그 동작으로 발생할 기대 이벤트, 수집 세션을 각각 기록한다. 화면 클릭1회가 네트워크·화면 변경 등 복수 이벤트를 만들 수 있으므로 “기대 이벤트10건”을 “사람 동작10회”와 동일시하지 않는다.

현행 구현은 `0.5*C1 + 0.3*(100-C2) + 0.2*C3`와 목표65%를 사용한다. C1은 필수 이벤트 일치율, C2는 전체 수집 행×필수 필드6개 대비 누락률, C3는 정의된 이벤트 유형8종의 커버리지다. 원본 행을 성공 사례만 남기도록 줄이거나 누락 필드를 임의 보충하지 않는다.

## M03 시나리오 생성 성공 — 사용자 승인 기준

2026-11-09 사용자는 생성 성공률과 정답 업무 흐름·순서 비교를 함께 적용하도록 승인했다. **생성 결과가 유효한 형식을 갖추고 사전에 정의한 정답 업무 순서를 충족한 경우 성공1건으로 센다.** 이 성공 조건은 미승인 제안으로 남기지 않고 사후 평가의 적용 기준으로 삼는다. 실제 정답 등록·생성기 연결·시험 검증과 최신 서명본 대조는 별도로 남는다. 공식 분모10·목표80%는 유지한다.

| 승인 기준·적용 계약 | 검사 내용 | 준비·확인 상태 |
| --- | --- | --- |
| 실제 생성 | 지정한 생성기가 업무당 요청을 받아 결과를 생성 | Mock 경로와 REAL HTTP/local argv 호출기 존재; 실제 최종 생성 adapter 연결 미확인 |
| 유효한 형식 | 업무/workflow ID 일치, `scenario_id,status,steps`, 단계별 `order,action,target` | 현행 구조 검사 존재 |
| 업무 절차 충족 | 동일한 절차 단위의 업무·workflow ID 및 `action,target` 대응 | 평가 전용 사전 정답 등록 필요; 생성 결과로 정답을 맞추지 않음 |
| 정답 업무 순서 | `EXACT_ACTION_TARGET_SEQUENCE`: 사전 정답의 전체 단계 순서 정확 일치 | 역순·누락·추가·임의 중복은 실패; 정답에 명시한 반복은 그대로 허용. 별칭·자동 보정 없음 |
| 전체 성공률 | 형식과 정답 순서를 모두 통과한 업무 수 / 사전 고정한 전체 업무 수 ×100 | 공식10업무·목표80% 유지. 실제 정답이 없으면 점수·개별 성공은 미평가 |

M02의75%를 M03에 적용하지 않는다. M02의 label 대응 정확도도 의미 순서 검증을 대신하지 않는다. GT는 생성 완료 후 평가에만 사용한다. 승인된 업무 정의는 생성 입력으로 사용할 수 있지만 평가 정답, 정답 일치 점수, PASS/FAIL을 생성기 입력이나 후보 선택에 넣지 않는다.

### 평가 정답과 준비 상태

평가 정답은 서버 관리 설정 `m03_evaluation_references[dataset_id]={path,sha256}`로 등록하며 기존 분석 manifest나 생성 입력을 수정하지 않는다. 정답 형식은 `m03-order-reference-v1`, `evaluation_only=true`, `matching_policy=EXACT_ACTION_TARGET_SEQUENCE`, `fixed_at`, `business_units[{business_unit_id,workflow_id,steps[{order,action,target}]}]`다. 초기 계약은 같은 절차 단위의 정확한 단계열 비교이며 자연어 유사도나 업무 의미 전체의 자동 추론을 추가하지 않는다.

정답이 없거나 일부 업무의 정답이 빠졌으면 전체는 `details.evaluation_status=NOT_READY`, `score=null`이다. 정답이 없는 형식 정상 항목의 `success`는 `null`이며, 확인된 형식 오류·생성 실패는 `false`로 남긴다. 형식이 정상인 생성·보관의 `COMPLETED`와 M04/M07 전달은 유지하지만 M03 순서 평가 통과로 표시하지 않는다. 등록된 정답의 해시·schema가 잘못되면 평가 `ERROR`다. 실제 정답은 아직 확보·등록이 필요하며 합성 예제를 공식 정답으로 대신하지 않는다.

정답 등록만으로 과거 결과를 덮어쓰지 않는다. 기존 생성 원본으로 재평가하려면 새 `external_run_id`·제출 시각을 사용해 결과 접수 API에 다시 제출한다. 원래 `origin_generation_id`·응답 SHA·생성 시각을 유지하며, 새 제출 시각은 접수 시각으로만 사용한다. 생성 후 정답을 등록한 평가는 `POSTHOC_REEVALUATION`, `official_pass=null`이다. 실제 생성기나 GPT를 다시 호출해야 하는 절차는 아니다. 기존 결과와 원본 SHA는 보존한다.

공식 대상은 manifest의 고유 업무 ID 10개다. 정답 10건·정상 결과 9건이면 누락 결과 1건도 실패로 세어 최대 90%이며 원본 결과 배열은 9건을 유지한다. 정답이 9건이면 결과가 9건 또는 10건이어도 `NOT_READY`, `score=null`이다. 대상 밖·중복 업무 ID 및 10건 초과 결과는 거부한다.

사용자가 제공한 `디딤돌_업무흐름_10.pdf`(SHA-256 `8f0fb27bf28de7d39d221d71781c82fae5456dcdfb0750205024fcf85bcbef72`)가 CU01~CU10 선정 근거다. 원문 절차 48개는 자연어 업무 단계이며 canonical UI/API 단계와 같은 단위라고 가정하지 않는다. CU09 상세조회와 기존 BU14 목록조회도 구분한다. 원문 기반 초안에는 실제 workflow/action/target과 사전 확정 시각을 임의로 채우지 않았고 평가 registry에도 등록하지 않았다.

### 저장소에서 찾은 연동 자료

| 자료 | 위치 | 재사용 범위 |
| --- | --- | --- |
| canonical 입력 helper | `model/workflow_candidate_v1_2/src/adapter.py:canonical_for_generator` | 절차 순서·action·target·event evidence 및 HTTP 특성의 생성기 입력 표현 |
| 기존 canonical 결과 | `model/workflow_candidate_v1/diagnostics/canonical_workflows.json` 10객체, `model/workflow_candidate_v1_2/diagnostics/canonical_workflows.json` 21객체 | 버전·process_model·업무 대응을 검토할 개발 산출물. 개수만으로 공식 업무 수를 증명하지 않음 |
| CSV 추론 함수 | `model/workflow_candidate_v1_2/src/infer.py:infer_csv` | 존재 확인만 수행. 이번 수정에서 모델을 실행하거나 결과를 재생성하지 않음 |
| REAL 연결 | `backend/m03_integration.py`, `backend/m03_http.py`, `backend/evaluators.py:call_adapter` | HTTP 또는 local argv. 외부 서버나 GPT 키가 반드시 필요한 구조는 아님 |

canonical은 `schema_version,process_model_id,procedures`를 담고 target도 객체여서 현행 M03 응답으로 그대로 반환할 수 없다. 이번에 추가한 `backend/m03_canonical_adapter.py`는 사전 선택한 canonical의 원본 순서·action·target·근거를 보존해 최종 `business_unit_id,workflow_id,scenario_id,status,steps`를 만든다. target 객체는 정렬 키·공백 없는 JSON 문자열로 고정하고 원본 객체도 별도 보존한다. 연결한 `DEV-CANON-PM-001 / WF-0037`은 DEVELOPMENT 변환 시험 1건이며 공식 업무 대응이나 새 모델 추론을 의미하지 않는다.

연결에 필요한 최소 작업은 사용할 canonical 버전·업무 대응 선택, 파일 SHA가 든 manifest 등록, 최종 시나리오 adapter 연결이다. 현행 REAL 입력에는 업무 정의와 분석 manifest가 필요하며 `source_run_id`와 manifest의 `workflow_ids`는 선택이다. 실행 가능한 별도 생성기가 있다면 그 경로나 명령만 추가 확인한다. 로컬 adapter를 쓰면 HTTP 주소·인증은 불필요하다.

`POST /api/m03/generate`와 `POST /api/integrations/m03/result`는 KTL 내부의 생성 요청·결과 접수 API이며 외부 M02 서버 주소가 아니다. 현재는 위 로컬 canonical adapter를 연결해 REAL 개발 요청·접수를 확인했다. 공식 10업무의 독립 분석 입력과 단계 단위 대응, 평가 정답의 사전 확정·등록은 남아 있다.

## M04 자동 실행의 평가 단위

회의 기준 초안은 **한 자동화 실행 안에서 동작·입력항목 등 약10개를 확인하는 구성**이다. 전체 스크립트를10번 반복하거나 독립 스크립트10건을 반드시 준비한다는 뜻으로 확정하지 않는다. 현행 공식 코드는 스크립트/테스트 수를 분모로 사용하므로, 이 차이를 합의하기 전에는 산식·분모를 변경하지 않는다. 목표90%도 현행 값을 유지한다.

각 항목에는 다음 정보를 사전에 붙인다.

| 필드 | 기록할 내용 |
| --- | --- |
| 항목ID·목적 | 어떤 업무 결과를 확인하는지 |
| 초기 조건 | 화면·로그인·기존 데이터·시험용 식별자 상태 |
| 동작·대상·입력 | 자동화 동작, 실제 선택자, 시험 입력 |
| 기대 결과 | 포커스/입력값/조회 응답/화면 반영/저장 완료 중 요구 범위 |
| 판정·근거 | 독립 검사 조건, 실행 시각, DOM/API 결과, 실패·시간초과 |

항목 단위가 승인된다면 `성공 항목 수/사전 고정한 전체 항목 수`로 검산하는 안을 검토한다. 이는 제안이며 현재 공식 코드의 스크립트 분모를 대체하지 않는다. 실행되지 않은 항목과 실패를 숨기거나 성공 항목만으로 분모를 줄이지 않는다.

현행 BU14 개발 예시는 명함 목록 열기, 검색 입력 포커스, 검색어 입력, 검색 요청·목록 확인, 재포커스, 검색어 지우기, 전체 조회 요청·목록 확인, 초기화 상태 확인의8단계다. 이를 임의 분할해10개로 맞추지 않는다. 이 업무에는 신규 저장·등록 단계가 없다.

자동 등록을 택한다면 입력칸 채우기만으로 성공 처리하지 않는다. 새 저장 요청 성공과 신규 레코드ID 또는 승인한 업무 키, 실제 목록/상세 반영을 확인한다. 실행 전에 이미 있던 레코드를 새 등록 성공으로 세지 않도록 초기 조건도 고정한다. 입력·조회 업무라면 해당 업무에서 요구하는 완료 범위만 검사한다.

## M07 입력20건 생성·검사

회의 방향은 **입력20건을 일괄 생성·검사**, 목표80%다. 입력20건이 반드시 서로 다른 업무20종이라는 조건은 확인되지 않았다. 같은 업무 안의 입력·조건이 다른 시나리오를 허용할지, 동일 입력의 반복을 허용할지는 별도 확정한다. 현재 UI의 중복 scenario ID 제한을 합의된 중복 정책의 근거로 삼지 않는다.

| 항목 | 현재 계약·초안 | 추가 확인 |
| --- | --- | --- |
| 입력 수 | 사전에20건을 고정하고 각 입력과 요청을 연결 | 업무 종류 수, 중복·반복 허용 기준 |
| 일괄 처리 | 현행 provider는 각 입력에 독립 요청을 순차 실행 | 단일 대형 요청을 필수로 만들지 않음 |
| 검사 범위 | 현행 공식은 문법 PASS와 실행 PASS를 모두 충족해야 성공 | 회의의 문법 중심 설명과 최종 제시기준서의 범위 대조 |
| 목표·분모 | 현행 공식 `both_pass_count/20*100`, 목표80% | 생성 자체 실패로20코드 미충족 시 처리 및 재시도 운영 확정 |
| 실패·재시도 | 원본 요청·응답·오류·시도ID를 남김; 현행 자동 재시도 없음 | 승인 없는 성공 응답만 선택/덮어쓰기 금지 |
| 원본 보관 | prompt·응답·추출 코드·SHA·문법/실행 결과 연결 | 빈 응답·실패도 근거 보관, 민감정보 마스킹 |

실제 GPT 코드 생성과 PREPARED 코드 파일 검사는 출처를 분리한다. PREPARED를 새 LLM 생성 실적으로 세지 않는다. 코드20건을 얻지 못한 상태를 현행 공식 시험 완료로 표시하지 않으며, 생성 실패 시도가 사라지지 않도록 별도 원본 로그를 유지한다.

## 독립 수정과 합의 후 작업

| 이번에 수정한 범위 | 별도로 남는 범위 |
| --- | --- |
| M01 워커 복원 중 자식 팝업 등록, 구판 smoke schema assertion | 실제 Chrome 워커 정지·팝업 시험, 시작 전 지연 이벤트 귀속 정책 |
| M03 JSON escape 인증값 차단, 형식·정답 순서 결합 평가, 공식 누락 분모와 원생성 시각/SHA 연결 | CU01~CU10 공식 분석 workflow 대응·같은 단위의 독립 정답 사전 등록·실제10건 시험 |
| M03 Windows 분할 본문 처리, canonical adapter 연결·REAL 개발1업무 실제 API 검증 | 새 입력의 수동 화면·브라우저 실행 검증과 공식 시험 |
| M07 빈 fence/공백 코드의 응답·prompt 근거 보존 | 입력20건·검사 범위·중복·재시도 기준과 실제 전체 시험 |

M04 판정 단위와 실제 등록 완료 조건도 합의 후 적용한다. 모델·공식 contract·GT 정책은 유지한다. 후속 회귀 복구에서 개행 변환된 승인 파일43개를 정확한 승인 bytes로 복구하고 누락된 역사 events.csv를 원본 SHA가 일치하는 파일로 복사했다. 이는 모델·승인 결과를 재생성한 작업이 아니며, 원래 bytes 백업·복구 SHA·불변 보호 대상은 별도 변경 보고서에 기록했다. 공식 분석 입력·정답과 실제 전체 시험이 필요한 작업을 개발 연결 완료 범위에 포함하지 않는다.

## 실제 시험 기록

각 시험은 기준 버전, 업무/입력ID, 원본 SHA, 실행 환경·시각, 요청/시도ID, 실제 결과, 실패 원인과 재시도를 보관한다. 원본 요청·응답은 비밀값을 제외하고 해당 입력·코드·실행 결과와 대응한다. 합성 회귀, 로컬 브라우저, 실제 업무1건, 공식 전체 시험을 구분해 보고한다.

최종 확인의 우선순위는 M03의 승인 기준에 따른 실제 정답 등록·평가 및 생성기 연결 검증, M04 평가 단위·항목별 완료 범위, M01 행동·이벤트·분모, M07 검사·실패·중복 기준이다. 실제 연동 자료는 위 저장소 자산을 먼저 사용하고 부족한 연결 지점만 요청한다.
